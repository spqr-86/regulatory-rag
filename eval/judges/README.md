# Citation judge — учебный черновик

Практика по LangChain Academy, курс Reliable Agents, модуль 2,
[LLM-as-a-Judge](https://langchain-ai.github.io/lca-lessons/reliable-agents/module-2/llm-as-judge).
Применяем материал курса к regulatory-rag. Код пишет учащийся;
ассистент объясняет по одному шагу, проверяет и запускает офлайн-тесты.

## Контракт

Вход: вопрос, ответ RAG и точные фрагменты, переданные генератору.
Модель сопоставляет документ, раздел и пункт/подпункт/статью для каждого
положения, возвращает только `checks`. Каждая запись содержит `field`,
`answer_quote`, `context_quote`, `comparison`, `reason`.

Код проверяет, что указанные цитаты действительно присутствуют в своих
текстах, и вычисляет статус (`validate_and_score`):

- `mismatch` и `missing_in_answer` по документу или пункту дают `fail`;
- иначе `unverifiable` даёт `needs_review`; только `match` дают `pass`;
- пустой массив даёт `needs_review`;
- `missing_in_answer` по `field=section` статус не меняет: документа и
  пункта достаточно, чтобы найти норму. Запись остаётся в `checks`;
- `missing_in_answer` с непустым `answer_quote` — противоречие судьи
  («нет в ответе», но с цитатой из ответа). Запись получает
  `contract_violation`, статус — `needs_review` (уже вычисленный `fail`
  не маскируется; для `section` статус не меняется).

Ошибкой формата ответа судьи (`ValueError`), а не ошибкой оцениваемого RAG,
остаются: выдуманные цитаты, пустые строки вместо цитат, неизвестный
`comparison`, `match`/`mismatch` без обеих цитат и `missing_in_answer`
без `context_quote`. Семантическое сравнение остаётся задачей модели.

`parse_verdict` принимает JSON и в ограде ```json, требует массив
`checks` из объектов с полями `field`, `answer_quote`, `context_quote`,
`comparison`, `reason`, допустимые значения `field`/`comparison` и
непустой `reason`. Общие `status`/`reason` судья не возвращает.

## Текущее состояние и следующий шаг

Правила статуса проверены офлайн-пересчётом сохранённых ответов судьи
на G001 и G006 (`eval/runs/citation_judge_*_2026-10-12/`, не в git):
G001 ошибка → `pass`, G006 `fail` → `pass`. Судья вызывается только разовыми скриптами
(`eval/runs/`, `run_citation_example.py`), в LangSmith-эксперимент пока
не подключён. При подключении — вторым показателем счётчик пропущенных
разделов (`section_missing`).

Известные ограничения:

- проверка цитаты — подстрока после нормализации; `answer_quote` без
  номера документа (например, без «2464») проходит `match`, код это не ловит;
- промпт с указаниями и few-shot против случая G001 судья проигнорировал —
  противоречие ловит код, а не промпт;
- `parse_verdict` снимает ограду через `strip`, который удаляет набор
  символов, а не префикс.

`run_citation_example.py` делает три реальных вызова модели через фабрику
проекта. Платные прогоны — только с отдельного разрешения. Не менять
production, индекс, RAG graph или общие настройки модели для продолжения
этого упражнения.

## Офлайн-проверки

```bash
.venv/bin/python -m pytest tests/eval_judges -q
```

51 проверка (`test_parse_verdict.py`, `test_validate_and_score.py`,
`test_judge_citations.py`) охватывает парсер, статусы и их приоритет,
наличие/тип цитат, правила для `section` и `contract_violation`, полный
вызов с подставной моделью. Это синтетические проверки кода, без сети;
они не доказывают качество семантических решений судьи.
