Retrieval Eval Increment — regulatory-rag

Спек. Создан 2026-09-01. Источник контекста: конспект LLM Zoomcamp модуль 4 (~/career/courses/llm-zoomcamp/notes/module-04-evaluation.md), handoff сессии 17.

Задача

Генеративный контур eval в regulatory-rag закрыт (correctness / faithfulness / OOS-отказ через eval/run_v7_eval.py). Дыра — offline-оценка поиска на реальном корпусе отсутствует: eval/retrieval_metrics.py (Hit Rate / MRR / nDCG) реализован и покрыт юнит-тестами, но нигде вне tests/ не вызывается. У golden set tests/dataset.csv нет колонки «вопрос → релевантный chunk_id», поэтому Hit Rate/MRR не на чем считать. Веса слияния и rerank тюнятся на глаз.

Инкремент добавляет три вещи по урокам 02–06 модуля 4: (1) генератор ground truth A→Q*→A' по корпусу, (2) прогон retrieval через существующий evaluate_retrieval_batch с получением baseline Hit Rate@k / MRR, (3) grid search параметров поиска по этим метрикам. Плюс ручная разметка существующих 57 вопросов как held-out валидации против завышения на синтетике.

Подходы

Вариант A — Per-chunk генератор + два изолированных прогона рекомендуемый

Генерация GT. Скрипт eval/generate_retrieval_gt.py: итерируется по всем чанкам коллекции Chroma (не по source_docs/ — берём ровно те чанки, что видит retrieval). Для каждого чанка один LLM-вызов со structured output Questions(questions: list[str]), промпт из урока 03 («эмулируй специалиста по ОТ, задай 3 вопроса, минимум слов из текста чанка, естественные формулировки»). Запись {"question": q, "chunk_id": passage_identity(chunk), "source": ..., "chunk_preview": ...} в eval/data/retrieval_gt.jsonl. Батч ThreadPoolExecutor(max_workers=6) + retry на 429/5xx, calc_total_price в конце. Фильтр мусорных чанков (< 200 символов, оглавления) до генерации. Дедуп вопросов: нормализация (lower, strip пунктуации) + отсев точных дублей; near-dup через косинус эмбеддингов > 0.95.

Прогон. Два тонких раннера поверх evaluate_retrieval_batch: 

eval/run_retrieval_eval.py --path simple    # vector+bm25 → rrf_merge(RRF_K, top_k)
eval/run_retrieval_eval.py --path complex   # vector → rerank(top_n) → mmr(MMR_LAMBDA)

Каждый раннер строит retrieval_fn(query) -> [chunk_id, ...], дёргая ровно движок нужного пути (вызвать внутренние функции из rag_simple/rag_complex в обход графа и роутера), прогоняет retrieval_gt.jsonl, печатает Hit Rate@{5,10,12}, MRR, пишет benchmarks/retrieval_eval_{path}_{date}.json.

Тюнинг. eval/tune_retrieval.py --path {simple|complex}. Simple: 1D-скан RRF_K ∈ {10,20,40,60,80}. Complex: grid rerank_top_n ∈ {3,5,8,12} × MMR_LAMBDA ∈ {0.3,0.5,0.7,0.9} (16 комбинаций). Обучение на синтетике, финальная цифра — на held-out 57. Лучшая комбинация пишется в отчёт с числом (не интуицией), применение в V7Config — отдельным ручным шагом после ревью.

Held-out. eval/label_golden_retrieval.py: для каждого из 57 вопросов dataset.csv прогнать retrieval top-20, показать кандидатов + ground_truth, оператор выбирает номер релевантного чанка (или «нет» → вопрос выпадает). Результат — колонка relevant_chunk_id в dataset.csv (или сайдкар tests/retrieval_golden.jsonl).

Изоляция: метрика поиска не смешана с роутером/генерацией — дыра #1 закрывается точно.

Максимум переиспользования: метрики, RRF, rerank, identity уже есть.

Held-out ловит завышение на синтетике (предупреждение уроков 05/15) численно.

Нужно аккуратно вызвать движок пути в обход графа — риск разойтись с прод-поведением, нужен тест на паритет.

Ручная разметка 57 вопросов — ~40–60 мин работы оператора.

Вариант B — Генерация по секциям документа, multi-chunk relevance

GT генерируется не по чанку, а по логической секции НПА (статья / пункт), релевантными считаются все чанки секции. evaluate_retrieval уже принимает список релевантных. Ближе к реальности регуляторки, где ответ размазан по пунктам.

Реалистичнее: Hit Rate не штрафует за «соседний абзац той же статьи».

Меньше шумных «промахов» от того, что вопрос покрывается двумя чанками.

Противоречит зафиксированному решению «ровно один чанк».

Нужна надёжная границаструктуры секций из docling-метаданных — не для всех 12 PDF одинаково чисто.

MRR теряет смысл «позиция первого точного попадания».

Вариант C — Прогон через полный граф V7, retrieval снимается из state

Не трогаем внутренности путей. Гоняем вопрос через весь граф (как run_v7_eval.py), из финального state["passages"] достаём chunk_id и считаем метрики. Роутер сам решает simple/complex.

Ноль риска разойтись с продом — это и есть прод-путь.

Минимум нового кода: хук в существующий раннер.

Метрика смешивает retrieval + роутер + rewrite. Плохой Hit Rate не говорит, где чинить — дыра #1 закрывается лишь частично.

«Раздельно simple/complex» не получить — роутер не заставить.

Тюнинг медленный и дорогой: каждая комбинация = полный прогон графа с LLM-вызовами вместо ~1 сек.

Вариант D — Внешний фреймворк (Ragas context precision/recall)

Отдать retrieval-оценку в Ragas: context_precision, context_recall поверх сгенерированного GT.

Меньше своего кода для метрик.

Конспект прямо решил «Ragas/DeepEval не берём» — контур глубже курсового, лишняя зависимость.

Ragas-метрики LLM-based → каждая grid-комбинация стоит денег, не ~1 сек.

Дублирует уже написанный и протестированный retrieval_metrics.py.

Критерии приёмки

  • eval/generate_retrieval_gt.py проходит по всем чанкам коллекции, пишет eval/data/retrieval_gt.jsonl со схемой {question, chunk_id, source, chunk_preview}
  • 3 вопроса на чанк; мусорные чанки (< 200 симв., оглавления) отфильтрованы до генерации
  • Дедуп: нет точных дублей вопросов; near-dup (косинус > 0.95) отсеяны, счётчик удалённых в логе
  • Скрипт печатает суммарную стоимость через calc_total_price; прогон укладывается в < $2, при прогнозе выше — abort с сообщением
  • Батч устойчив к 429/5xx: retry с backoff, одиночный сбой чанка не роняет весь прогон
  • eval/run_retrieval_eval.py --path simple строит retrieval_fn на движке rag_simple и печатает Hit Rate@{5,10,12}, MRR на retrieval_gt.jsonl
  • --path complex то же на движке rag_complex (vector → rerank → MMR)
  • Тест паритета: retrieval_fn обоих путей на 5 контрольных запросах даёт тот же список chunk_id, что полный граф с форсированным путём
  • Результаты пишутся в benchmarks/retrieval_eval_{path}_{YYYY-MM-DD}.json, формат совместим с будущим A/B в compare.py
  • eval/tune_retrieval.py --path simple сканирует RRF_K, выводит таблицу «параметр → Hit Rate@10, MRR», отмечает лучшую
  • --path complex — grid rerank_top_n × MMR_LAMBDA, та же таблица
  • Тюнинг: обучение на retrieval_gt.jsonl, итоговая цифра лучшей комбинации подтверждена на held-out 57 — обе цифры в отчёте
  • Лучшие параметры не применяются к V7Config автоматически — только рекомендация в отчёте + ручной PR
  • eval/label_golden_retrieval.py добавляет relevant_chunk_id к 57 вопросам; вопросы без релевантного чанка помечены и исключены из held-out метрики
  • Отчёт-сводка (markdown в benchmarks/ или дополнение eval/README.md): baseline до/после тюнинга, Hit Rate@k кривая, разрыв синтетика↔held-out, вывод по каждому пути
  • Если Hit Rate на синтетике > 0.95 — в отчёте явное предупреждение «вопросы слишком близки к тексту чанка, доверять held-out»
  • eval/README.md обновлён: retrieval_metrics.py больше не «мёртвый», описаны новые скрипты и порядок запуска
  • Юнит-тесты на generate_retrieval_gt (парсинг structured output, дедуп, фильтр мусора) и на построение retrieval_fn (моки движков)

Открытые вопросы к реализации

  • Индекс Chroma локально не построен (chroma_db/ пуст) — до прогона нужен python -m src.indexing...; число чанков после билда уточнить (оценка: 12 PDF → ~800–1500 чанков → ~2400–4500 вопросов)
  • Формат held-out меток: колонка в dataset.csv vs сайдкар tests/retrieval_golden.jsonl — решить при реализации (сайдкар безопаснее, не ломает run_v7_eval.py)
  • Целевой порог Hit Rate@10 как gate в CI — пока не назначаем, сначала смотрим baseline
