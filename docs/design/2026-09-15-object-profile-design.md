# Regulatory RAG — сведения об объекте подразделения (ObjectProfile): спецификация

Дата: 2026-09-15. Статус: **согласована в brainstorming, исправлена по внешнему ревью
(gpt-6-astra, 15.09), реализована** (issue #44, смержено 16.09.2026).
Дополняет [спецификацию MVP Q&A для подразделений](./2026-09-14-department-qa-mvp-design.md)
(§5 модель документов, §8 контракт, §11 evaluation). Второй контракт ответа не заводится (П7).

## 1. Проблема

Лист особенностей объекта защиты подразделения сейчас индексируется как обычный внутренний
документ (`scope: unit`). Смоук 15.09 (6 вопросов, gpt-4o-mini, коллекция `department_demo`)
показал три провала, которые поиском не лечатся:

| Подразделение | Вопрос | Что пошло не так |
|---|---|---|
| `unit_dispatch` | Сколько огнетушителей и нужен ли план эвакуации? | Разделы листа вытеснены общими ЛНА из top-8; численность объекта в ответ не попала |
| `unit_office` | Тот же вопрос | Норма ППР найдена, но `external_basis` пуст → `needs_review` |
| не выбрано | Нужен ли на нашем объекте план эвакуации? | Ответ «да» вместо `needs_context` |

Факт объекта (численность, системы, дежурство) — не норма и не фрагмент для ранжирования: он
нужен в каждом ответе по этому подразделению целиком. Поэтому лист передаётся структурой,
а не поиском.

## 2. Решения

### 2.0. Что гарантирует `answered` (решение Петра 15.09, вариант А)

`answered` = **ответ со сверенными ссылками**: каждая цитата существует, у неё правильная
роль, блокирующих уточнений нет, есть нормы обоих уровней (кроме `fact_only`), процитированный
профиль датирован, эвристика §2.3 не нашла нормативного вывода в фактах объекта.

`answered` **не гарантирует**:

1. что процитированный фрагмент подтверждает утверждение (ссылка может быть нерелевантной);
2. что ответ полон: `decide()` не знает, из каких частей состоит вопрос;
3. что свободный текст `answer` не содержит утверждений сверх списков.

Эти свойства проверяет eval (§5.2: обязательные подответы, запрещённые выводы), а не рантайм.
Следствия:

- UI: баннер `answered` — «Ссылки сверены: законодательство и ЛНА. Смысл ответа не проверен
  специалистом». Текст «Ответ подтверждён…» убирается.
- UI показывает структурные списки (основания, факты объекта, применение) основным блоком,
  `answer` — подписью «Краткий черновик».
- В README/доках статус описывается этими же словами; «доказанно безопасный ответ» не пишется.
- Условие пересмотра: если eval покажет, что `answered` систематически скрывает неверный
  вывод, вводится проверка обоснованности (LLM-судья или ручная разметка) отдельной спекой.

### 2.1. Гранулярность: разделы, не поля

`ObjectProfile` = разделы шаблона листа `obj_s1 … obj_s9` с исходным текстом раздела.

```python
class ObjectSection(BaseModel):
    id: str  # obj_s1 … obj_s9
    number: int  # номер раздела шаблона
    title: str  # «Системы противопожарной защиты объекта»
    text: str  # исходный текст раздела
    presence: Literal["present", "empty", "missing"]


class ObjectProfile(BaseModel):
    unit_id: str
    document_id: str
    source: str  # имя файла листа
    content_sha256: str  # хеш файла на момент загрузки
    title: str
    as_of_date: Optional[date]  # «Дата заполнения»; плейсхолдер [дата] → None
    sections: dict[str, ObjectSection]
```

- `presence`: `present` — у раздела есть непробельный текст; `empty` — заголовок есть, текста
  нет; `missing` — заголовка раздела в листе нет. Парсер содержание не понимает, поэтому
  known/unknown/not_applicable не вводятся.
- **Ограничение:** «Информация уточняется» — это `present`. Неизвестность факта внутри текста
  раздела распознаёт модель, не парсер; это семантическое свойство, проверяется только eval
  (вопрос 9, §5.2).
- Раздел 6 «Контактные телефоны объекта» парсится, но в промпт и `evidence` не передаётся.
- Structured-поля (численность, категории как числа/enum) — только если eval покажет
  систематическую ошибку применения факта. В этой итерации не делаются.

**Грамматика листа (один поддерживаемый Markdown-шаблон).** Универсального парсера нет.

1. Первая непустая строка — заголовок листа `## Лист особенностей объекта защиты…` →
   `ObjectProfile.title`. Текст до первого раздела — преамбула, в разделы не входит.
2. Любая строка, начинающаяся с `## `, закрывает предыдущий раздел.
3. Заголовок раздела — `## N Название`, N от 1 до 9. Название сверяется с таблицей шаблона
   после `casefold` и схлопывания пробелов; несовпадение → `ObjectProfileError`.
4. Любой другой `## `-заголовок после заголовка листа (`## 10 Примечания`, `## Приложение`)
   → `ObjectProfileError`. Молча приклеивать его к разделу 9 нельзя.
5. Повтор номера → `ObjectProfileError`. Ни одного раздела → `ObjectProfileError`.
6. Дата: строка `Дата заполнения: <значение>` в любом месте листа, **вырезается** из текста
   раздела. Значение `ДД.ММ.ГГГГ` (точка в конце допустима) → `date`; `[дата]` → `None`;
   строки нет → `None`; любое другое значение или некорректная дата → `ObjectProfileError`;
   больше одной строки → `ObjectProfileError`.

| N | Название шаблона |
|---|---|
| 1 | Ответственный за пожарную безопасность на объекте |
| 2 | Категории помещений по взрывопожарной и пожарной опасности |
| 3 | Системы противопожарной защиты объекта |
| 4 | Первичные средства пожаротушения |
| 5 | Дежурный персонал |
| 6 | Контактные телефоны объекта |
| 7 | Планировка и эвакуация |
| 8 | Технические особенности |
| 9 | Складские и подсобные помещения |

### 2.2. Давность

- Порога давности в коде нет.
- `as_of_date` показывается в ответе (`profile_as_of_date`) и в UI.
- Ответ процитировал хотя бы один `obj_s*`, а `as_of_date is None` →
  `needs_review` + `object_profile_undated`.
- Синтетические листы `unit_office` (01.09.2026), `unit_dispatch` (28.08.2026),
  `unit_depot` (25.08.2026) датированы 15.09. Без даты остаётся только `unit_partial`.

### 2.3. Контракт внутри `ModelAnswer`

`external_basis` / `internal_basis` не меняются. Добавляются:

```python
class ObjectFact(BaseModel):
    statement: str
    evidence_ids: list[str] = []  # по промпту — только obj_s*


class AppliedConclusion(BaseModel):
    statement: str
    evidence_ids: list[str] = []  # по промпту — ≥1 obj_s* и ≥1 ext_*/int_*


class ModelAnswer(ModelAnswerV1):  # ModelAnswerV1 = текущая схема без новых полей
    object_facts: list[ObjectFact] = []
    applied_conclusions: list[AppliedConclusion] = []
```

**Схема против `decide()`.** Схема (Pydantic, structured output) проверяет только типы.
Пустые `evidence_ids`, applied без нормы, роли ссылок, уточнения — всё проверяет `decide()`.
Валидаторы на эти инварианты в схему не добавляются: иначе ответ модели упадёт в
`failed/generation_failed` вместо предусмотренного статуса.

`Level` расширяется значением `"object"`, префикс `obj_` → `object`.

Сигнатура:

```python
def decide(
    answer: ModelAnswer,
    evidence: dict[str, Evidence],
    profile_as_of: Optional[date] = None,
) -> tuple[Status, list[str]]
```

Отличать «профиля нет» от «профиль без даты» `decide()` не нужно: без профиля `obj_*` нет в
`evidence`, и любая такая ссылка уже `citation_invalid`. Поэтому `cites_object` и
`profile_as_of is None` означают ровно недатированный профиль.

Определения:

- `has_ext` / `has_int` — есть хотя бы один `ext_*` / `int_*` в `external_basis` /
  `internal_basis` **или** в `applied_conclusions`. Ограничение: один applied со ссылками
  обоих уровней закрывает оба уровня, релевантность ссылок не проверяется (§2.0 п. 1).
- `cites_object` — есть хотя бы один `obj_*` в `object_facts` или `applied_conclusions`.
- `fact_only` — `object_facts` не пуст, `applied_conclusions` пуст, `has_ext` и `has_int` ложны.
- `empty_answer` — все четыре списка пусты и `clarifying_questions` пуст.
- `normative_fact` — `statement` хотя бы одного `ObjectFact` содержит нормативный маркер:
  регистронезависимое вхождение по границе слова одной из основ
  `требуется|не требуется|необходим|должен|должн[аоыуе]|достаточн|допуска|запрещ|обязан|
  не снижа|не менее|не более`. Список закрытый и лежит константой в `contract.py`.
  Это эвристический сторож от самого частого обхода (нормативный вывод выдан за факт),
  а не классификатор. `должность` под маркер не попадает.

Псевдокод, порядок строк = порядок проверок:

```python
if answer.out_of_scope:
    return "out_of_scope", []
if check_citations(answer, evidence):  # любая строка группы «цитаты» ниже
    return "failed", ["citation_invalid"]
if answer.clarifying_questions:  # ЛЮБОЙ непустой список
    return "needs_context", ["applicability_unclear"]
reasons = []
if applied_without_norm:
    reasons.append("applied_without_norm")
if normative_fact:
    reasons.append("object_fact_normative")
if not fact_only and not has_ext:
    reasons.append("external_evidence_missing")
if not fact_only and not has_int:
    reasons.append("internal_evidence_missing")
if cites_object and profile_as_of is None:
    reasons.append("object_profile_undated")
if answer.possible_mismatch and has_ext and has_int:
    reasons.append("possible_mismatch")
return ("needs_review" if reasons else "answered"), reasons
```

Группа «цитаты» (`check_citations`, любая → `failed` / ровно `["citation_invalid"]`):

| Ситуация |
|---|
| Пустой `evidence_ids` у любого элемента (`Basis`, `ObjectFact`, `AppliedConclusion`) |
| Несуществующий id, в том числе `obj_s*` при непереданном профиле |
| Уровень перепутан: `ext_`/`int_` в `object_facts`, `obj_` в `external_basis`/`internal_basis` |
| Ссылка на раздел `missing`, `empty` или раздел 6 — они не кладутся в `evidence`, это частный случай «несуществующего id» |
| `applied_conclusions` без `obj_*` |

Остальные строки:

| Ситуация | Статус / reason |
|---|---|
| `clarifying_questions` не пуст — **независимо от наличия норм** (изменение против v1, ревью 1.2) | `needs_context` / `applicability_unclear` |
| `applied_conclusions` с `obj_*`, но без `ext_*`/`int_*` | `applied_without_norm` |
| `normative_fact` | `object_fact_normative` |
| `fact_only` | `external_evidence_missing` / `internal_evidence_missing` **не** добавляются |
| Не `fact_only`, включая `empty_answer` | `external_evidence_missing` / `internal_evidence_missing` по `has_ext` / `has_int`, как в v1 |
| `cites_object` и `profile_as_of is None` | `object_profile_undated` |
| `possible_mismatch` при `has_ext` и `has_int` | `possible_mismatch` (как в v1) |

Пустой ответ (`empty_answer`) → `needs_review` /
`["external_evidence_missing", "internal_evidence_missing"]`.

Обоснование `fact_only → answered`: вопрос «кто ночью принимает сигнал» — вопрос о факте
объекта, нормы в нём нет; v1 штрафовал его `external_evidence_missing`.

**Требование двух уровней при любом applied сохраняется** (продуктовое решение основной
спеки: сотруднику нужны и закон, и ЛНА). Узкий вывод, которому достаточно внешней нормы,
получит `needs_review` / `internal_evidence_missing`. В eval такой статус — ожидаемое поведение,
а не ухудшение.

**`answer` и полнота.** Промпт v2 требует: `answer` не содержит утверждений, которых нет в
списках; каждая часть составного вопроса либо отвечена в списках, либо названа в `answer` как
«не найдено», либо вынесена в `clarifying_questions`. Рантайм это не проверяет (§2.0).

### 2.4. Поток данных

1. `corpus/manifest.yaml`: у листа `role: object_profile` (остальные документы — без `role`).
   Валидация: `role: object_profile` допустим только при `source_type: internal`, `scope: unit`;
   не больше одного листа на `unit_id`. `Manifest` получает поле
   `object_profiles: dict[unit_id, file]` — `role` в метаданные чанков не пишется.
2. `apply_manifest` отбрасывает чанки документов с `role: object_profile` — листы не попадают
   в Chroma. BM25 строится в памяти из той же коллекции (`init_v7_pipeline` →
   `iter_all_documents`), отдельного BM25-набора нет: коллекция без листов даёт BM25 без листов.
3. Новый модуль `src/department_qa/object_profile.py`: `load_profiles(manifest, source_dir)
   → dict[unit_id, ObjectProfile]`; `source_dir` передаёт `wiring.py` из
   `settings.SOURCE_DOCS_PATH`. Нарушение грамматики §2.1 → `ObjectProfileError` при старте
   (ошибка данных, не деградация). `unit_id` профиля берётся из manifest, `source` и
   `content_sha256` — из файла.
4. `answer_question(..., profile: Optional[ObjectProfile])`:
   - **до поиска** проверяется `profile is None or (unit_id is not None and
     profile.unit_id == unit_id)`; нарушение → `failed` / `profile_mismatch` (ошибка
     интеграции, не нехватка контекста);
   - разделы `present` (кроме 6) становятся evidence уровня `object` с id `obj_sN` в том же
     словаре `evidence`. Поля: `title` — название листа, `locator` — «N <название раздела>»,
     `source` — `profile.source`, `document_id` — из manifest. Разделы `missing`, `empty` и
     раздел 6 в `evidence` не кладутся;
   - `decide(model_answer, evidence, profile_as_of=profile.as_of_date if profile else None)`.
5. Промпт `department_answer` **v2** (v1 остаётся в registry):
   блок «СВЕДЕНИЯ ОБ ОБЪЕКТЕ» с датой заполнения и разделами;
   - подразделение не выбрано → «объект не выбран»; вопрос, зависящий от объекта, →
     `clarifying_questions`;
   - подразделение выбрано, листа нет → пометка «лист не предоставлен», факты не придумывать;
   - раздел `empty` показывается как «(не заполнено) — ссылаться нельзя», раздел `missing` —
     «(раздела нет в листе) — ссылаться нельзя».
   Правила: `object_facts` — только наблюдаемые факты объекта со ссылками `obj_*`, без слов
   «требуется / достаточно / должен / не снижается»; вывод о применимости нормы — только в
   `applied_conclusions` (факт объекта плюс норма); норма без факта — в
   `external_basis`/`internal_basis`; отсутствие сведений формулировать как отсутствие, не
   подменять положительным фактом; правила `answer` и полноты — §2.3.
   `PromptVars` расширяется полями `object_label` и `object_sections` со значениями по
   умолчанию; v1 рендерится из того же класса и новые поля игнорирует.
6. `DepartmentResponse` + `object_facts`, `applied_conclusions`, `profile_as_of_date`,
   `profile_sha256`. Сервис:
   - `evidence` в ответе — **только процитированные** id из всех четырёх списков. Fallback
     «ничего не процитировано → все найденные» удаляется: нет цитат → `evidence=[]`;
   - `out_of_scope` → стандартный `next_step`, `answer=""`, все списки и `evidence` пусты
     (ранний выход `decide()` сохраняется, содержимое модели не показывается);
   - `citation_invalid` → основания и факты скрыты, как в v1.
7. **Режим — один комплект, переключается атомарно.** Настройка `DEPARTMENT_QA_MODE`:

   | Режим | Путь Chroma | Коллекция | Профили | Промпт | Схема structured output |
   |---|---|---|---|---|---|
   | `v1` | `./chroma_db_dept` | `department_demo` (листы в индексе) | не загружаются, `profile=None` | `department_answer` v1 | `ModelAnswerV1` |
   | `v2` | `./chroma_db_dept_v2` | `department_demo_v2` (без листов) | `load_profiles` | `department_answer` v2 | `ModelAnswer` |

   Пути разные, потому что `index.py` удаляет всю папку `CHROMA_DB_PATH` перед записью (найдено при
   планировании 15.09). `wiring.ensure_store_matches` падает при несовпадении пары с режимом.

   `wiring.py` собирает комплект по режиму; версия промпта задаётся режимом, а не отдельным
   `active_version`. По умолчанию `v1` до разбора парного прогона.
8. Streamlit-страница: блок «Сведения объекта» (процитированные разделы и дата заполнения),
   баннер и порядок блоков по §2.0.

## 3. Вне этой итерации

Обогащение поискового запроса полями профиля; LLM-rewrite запроса; профиль через tool-call;
разбор произвольных DOCX листов; порог давности в коде; structured-поля (§2.1); проверка
обоснованности и полноты в рантайме (§2.0); версионирование профилей сверх хеша; полноценные
пользователи. Позже, в eval MVP (§11 основной спеки): ~40 случаев, gold как «норма + факты».

## 4. Тестовые данные

- **Листы — только наблюдаемые факты.** 15.09 из `unit_office`, `unit_dispatch`,
  `unit_depot` удалены нормативные выводы составителя («план не требуется», «количество
  огнетушителей не снижается», «50 % расчётного количества, так как…», «не более 30 м»,
  причины в скобках у «план разработан»). В офисном листе добавлено: численность на этаже
  бизнес-центра — «информация уточняется у арендодателя»; огнезащитная обработка —
  «информация уточняется у арендодателя». Стоп-лист прогнан, чисто.
- 4-й синтетический лист `source_docs_dept/int_unit_partial_list.md` (gitignored, как
  остальные), `unit_id: unit_partial`: одновременно **ровно 50 человек, все на одном этаже**
  (точка границы, а не «~50»), раздел 5 «Дежурный персонал» отсутствует, «Дата заполнения»
  не указана. Запись в manifest с `role: object_profile`; стоп-лист прогоняется.
- **Воспроизводимость.** Листы gitignored, поэтому до обеих сборок корпус замораживается, а в
  лог прогона пишутся sha256 всех файлов `source_docs_dept/`, `corpus/manifest.yaml`,
  имя коллекции и число чанков, параметры поиска (`TOP_K_PER_LEVEL`, RRF). Unit-тесты
  используют собственные маленькие фикстуры в `tests/`, не файлы из `source_docs_dept/`.

## 5. Проверка

### 5.1. Unit-тесты (без сети)

- Парсер: 9 разделов → `present`; пустой раздел → `empty`; нет заголовка → `missing`;
  «Информация уточняется» → `present`; `[дата]` и отсутствие строки → `as_of_date=None`;
  `15.09.2026` и `15.09.2026.` → `date`; `32.13.2026`, `сентябрь 2026`, две строки даты,
  `## 10 Примечания`, неверное название раздела, повтор номера, ноль разделов →
  `ObjectProfileError`; строка даты вырезана из текста раздела; `source` и `content_sha256`
  заполнены.
- Manifest: `role: object_profile` у external или `scope: company` → `ManifestError`; два листа
  на один `unit_id` → `ManifestError`; `apply_manifest` отбрасывает чанки листа.
- `decide` — каждая строка таблиц §2.3 отдельным кейсом, плюс **пересечения** (точный статус
  и упорядоченный список причин):

  | Пересечение | Ожидание |
  |---|---|
  | уточнение + нормы обоих уровней | `needs_context` / `["applicability_unclear"]` |
  | уточнение + невалидная цитата | `failed` / `["citation_invalid"]` |
  | `out_of_scope` + невалидная цитата | `out_of_scope` / `[]` |
  | applied без нормы + недатированный профиль | `needs_review` / `["applied_without_norm", "external_evidence_missing", "internal_evidence_missing", "object_profile_undated"]` |
  | факт + внешняя норма, без applied | `needs_review` / `["internal_evidence_missing"]` |
  | пустой ответ | `needs_review` / `["external_evidence_missing", "internal_evidence_missing"]` |
  | нормативный факт + обе нормы, датирован | `needs_review` / `["object_fact_normative"]` |
  | ссылка на `empty`-раздел | `failed` / `["citation_invalid"]` |

- **Негативные `answered`** — ответы-обходы из ревью, которые больше не проходят:
  «План эвакуации для офиса не требуется» в `object_facts` → `object_fact_normative`;
  уточнение при двух нормах → `needs_context`; факт со ссылкой на `empty` → `citation_invalid`.
  Отдельным тестом фиксируется **известное ограничение**: applied с нерелевантными, но
  существующими ссылками обоих уровней → `answered` (тест документирует границу §2.0, а не
  желаемое поведение).
- Регрессия v1-кейсов без профиля; тест `clarifying_questions` при двух нормах переписывается
  под новое правило.
- `answer_question`: `obj_*` попадают в evidence; `empty`, `missing` и раздел 6 — нет;
  профиль чужого подразделения и профиль при `unit_id=None` → `failed` / `profile_mismatch`
  без вызова поиска и модели; нет цитат → `evidence=[]`; `out_of_scope` → пустые `answer`,
  списки и `evidence`; без профиля в промпте «объект не выбран» / «лист не предоставлен».
- Wiring: режим `v1` и `v2` собирают комплект §2.4 п. 7 целиком (коллекция, профили, промпт,
  схема).
- Промпт v2: рендер через `PromptVars`, блок объекта, `empty` → «(не заполнено)».
- View: баннер `answered` — текст §2.0.

**База красных тестов — конкретный список**, а не число. Замер 08.09 (CLAUDE.md проекта):
`test_agent_tools` ×2, `v7/test_bridge_rerank` ×3. Первым шагом плана пересчитать и записать
точные node id в план. Критерий: ни один тест вне списка не красный; тест из списка, ставший
зелёным, отмечается, но не прячет новую поломку.

### 5.2. Парный прогон v1 vs v2 (платный, согласован 15.09)

**Дизайн сравнения:** способы подачи сведений об объекте **на общей новой обвязке** — новый
`decide()`, новый сервис, одинаковые retrieval-параметры. Контроль `v1` — режим `v1` §2.4 п. 7
(лист в индексе, промпт v1, схема `ModelAnswerV1`). Это **не** воспроизведение поведения до
15.09: правило уточнений и удаление fallback действуют в обоих режимах. В выводах так и
пишется.

| # | Подразделение | Вопрос | Что проверяет |
|---|---|---|---|
| 1 | `unit_office` | Сколько огнетушителей должно быть на объекте и нужен ли план эвакуации? | составной вопрос, требуемое ≠ фактическое |
| 2 | `unit_dispatch` | Тот же вопрос | то же, объект с АУГП и 60 чел. |
| 3 | `unit_depot` | Действует ли у нас инструкция для складских помещений и когда испытывать наружную пожарную лестницу? | факт + норма |
| 4 | не выбрано | Нужен ли на нашем объекте план эвакуации? | `needs_context` |
| 5 | `unit_office` | Кто принимает сигнал пожарной сигнализации ночью? | `fact_only` |
| 6 | `unit_office` | Как оформить ежегодный отпуск? | `out_of_scope` |
| 7 | `unit_partial` | Нужен ли на нашем объекте план эвакуации? | граница ровно 50 |
| 8 | `unit_partial` | Кто у нас принимает сигнал пожарной сигнализации ночью? | раздел 5 отсутствует |
| 9 | `unit_office` | Есть ли огнезащитная обработка конструкций в зоне офиса и как часто её проверять? | `present`, но факт неизвестен, профиль датирован |

- **Порядок сборки коллекций.**
  1. Заморозить корпус: четыре листа окончательные (выводы вычищены, даты §2.2, лист
     `unit_partial` §4), остальные документы не меняются. Записать хеши §4.
  2. `unit_partial` добавить в manifest **без** `role`, пересобрать `department_demo` текущим
     `index.py` — база v1 на тех же данных. Дальше `department_demo` не пересобирается до
     конца сравнения.
  3. Поставить `role: object_profile` у четырёх листов, собрать `department_demo_v2`.
  4. Проверить наличие листов в `department_demo` и отсутствие в `department_demo_v2` — по
     `source` в Chroma и по результату поиска через `make_hybrid_search_fn` (оба канала).
- Скрипт `eval/run_object_profile_pair.py` запускает режимы `v1` и `v2` через тот же wiring,
  что UI. Сохраняет в `eval/runs/object_profile_pair_<дата>/` для каждого вызова: промпт,
  сырой ответ модели, переданные evidence, `DepartmentResponse`; плюс конфигурацию (модель,
  temperature, top_k, коллекция, хеши §4).
- Модель `gpt-4o-mini`, temperature 0, 18 вызовов (9 × 2), оценка < $0.05 — в пределах
  согласованного 15.09 бюджета.
- **Ожидания** записываются в `eval/data/object_profile_pair_expectations.yaml` и коммитятся
  **до** прогона. Gold строится независимо от формулировок листов. Для каждого вопроса:
  1. обязательные подответы;
  2. допустимые альтернативы формулировок и источников;
  3. запрещённые выводы (проверяются в `answer` **и** во всех списках, независимо от статуса);
  4. достаточные и недостающие факты объекта;
  5. ожидаемые статус и точный упорядоченный список причин **отдельно для v1 и v2**, либо
     заранее объяснённые альтернативы;
  6. источники по `document_id` + раздел/пункт, а не по динамическим `int_001`/`obj_s5`;
  7. для вопросов 1, 2, 7: норма, пункт, редакция, оператор сравнения и к чему относится
     численность (объект / этаж / здание) — из фрагмента корпуса, сверенного с официальным
     источником при записи ожиданий;
  8. правило частичного успеха: подответ засчитывается, только если нет запрещённого вывода.
- **Итог — три отдельных числа** на версию, не одно:
  1. поведение по контракту своей версии (статус + причины) из 9;
  2. обязательные подответы — засчитано / всего;
  3. запрещённые выводы — сколько встретилось.
  Плюс разбор каждого расхождения. Ожидания по `obj_s*` входят только в число 1 для v2 и не
  штрафуют v1. Судья-LLM не используется, сверка ручная.
- N=9, по одному вызову — девять наблюдений, не замер качества и не устойчивая разница версий;
  в выводах так и пишется.

## 6. Критерии готовности

- Unit-тесты §5.1 зелёные; красные только из списка базы §5.1.
- Листы есть в `department_demo` и отсутствуют в `department_demo_v2` — по Chroma и по
  гибридному поиску (§5.2 порядок, шаг 4).
- Файл ожиданий закоммичен раньше лога прогона; лог содержит хеши и сырые ответы.
- UI и доки описывают `answered` словами §2.0.
- Результат парного прогона (три числа на версию) и разбор записаны в `docs/roadmap.md`;
  решение — в `docs/explanation/design-decisions.md` (§10).
