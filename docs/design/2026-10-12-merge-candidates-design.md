# Склейка кандидатов complex-пути: MMR по оценке реранкера

Дата: 2026-10-12. Статус: дизайн согласован Петром, спек на ревью.
Источник проблемы: разборы трейсов G001 и G020 —
`docs/evaluation/experiments/langsmith-learning-2026-10-09/g001-program-a-trace-review.md`,
`.../g020-drivers-medical-trace-review.md`.

## Проблема

На complex-пути `evaluate_complex._candidates` строит кандидата `merged`:

1. `merge_all_passages` складывает все попытки (simple + complex), дедуплицирует и вызывает
   `mmr_select(top_k=24)`.
2. Поверх результата первые `SIMPLE_TOP_K=12` мест отдаются якорям — началу
   `fallback_snapshot` (упакованный контекст simple), затем `novel` из шага 1, обрезка до 24.

`mmr_select` берёт релевантность как `vector_score or rerank_score or score`. У complex-кандидатов
есть `vector_score`, поэтому порядок реранкера (cross-encoder, лучшая доступная оценка)
игнорируется. Нужные чанки высоко у реранкера выпадают из top-24 ещё до шага 2:

- G001: 2464#109 — 6-й у реранкера, 14-й после MMR, отсечён шагом 2; 2464#105 — 9-й у
  реранкера (`rerank_score` 0.9973, `vector_score` 0.5469), в top-24 не попадает.
- G020: 29н#319 — 2-й у реранкера, в top-24 не попадает.

Кандидат `last_attempt` содержит нужные чанки, но в обоих трейсах его отвергла валидация, и
итоговым стал `fallback_snapshot` без них.

## Решение

### 1. `mmr_select`: релевантность — сначала оценка реранкера

```python
relevance = p.get("rerank_score") or p.get("vector_score") or p.get("score", 0.0)
```

У simple-кандидатов `rerank_score` нет — для них поведение не меняется. Формула MMR, штраф
за повтор `doc_id` и `mmr_lambda` из плана не меняются.

### 2. `_candidates`: якоря + MMR только по complex-пулу

```
anchors = fallback_snapshot.passages[:SIMPLE_TOP_K]          # как сейчас
pool    = passages последней complex-попытки, кроме anchors   # без simple-попытки
merged  = anchors + mmr_select(pool, FINAL_MERGE_TOP_K - len(anchors), plan.mmr_lambda)
```

- Simple-попытка в общий пул больше не идёт: её лучшая часть уже стоит якорями, а её
  `vector_score`/RRF-оценки несопоставимы с `rerank_score`.
- Нет snapshot или он пуст → `anchors = []`, все 24 места из complex-пула по MMR.
- Реранкер упал → complex-попытка пуста (`rag_complex` обнуляет `passages`). Пул без новых
  чанков → `merged` пуст: одни якоря повторно паковали бы уже упакованный snapshot и выдавали
  его как `complex_sufficient` (уточнено при реализации 12.10, инвариант
  `test_packed_snapshot_is_not_expanded_again`). Дальше, как и сейчас, проверяются
  `last_attempt` и `fallback_snapshot`.
- Реранкер не подключён (`rerank is None`) → у кандидатов нет `rerank_score`, MMR работает по
  `vector_score`, как сейчас.
- Кандидаты `last_attempt` и `fallback_snapshot` не меняются.

Граф гарантирует не больше одной complex-попытки (`rag_complex` дедуплицирует по
`retrieval_id`); `fallback_snapshot` выставляется всегда при маршруте `complex`
(`evaluate_triage`).

### 3. `merge_all_passages`

После правки `_candidates` не вызывает `merge_all_passages`. Других вызовов в `src/` нет;
`eval/triage_calibration.py` использует `_candidates` и получает новое поведение автоматически.
`merge_all_passages` удаляется вместе со своими тестами; `mmr_select` остаётся (его вызывает
`_candidates`), докстринг поправить.

## Рассмотренные варианты (офлайн, сохранённые входы evaluate_complex)

Место целевого чанка в упакованном контексте (`_prepare` без expander и LLM), из 24:

| | сейчас | V1: якоря + порядок реранкера | **MMR по реранкеру** (λ=0.7 / 0.5) |
|---|---|---|---|
| G001 #109 | — | 16 | 17 / 17 |
| G001 #105 | — | 19 | 19 / 19 |
| G020 #319 | — | 14 | 14 / 15 |

Отвергнуты: V1 (без MMR) — чинит так же, но убирает разнообразие документов, которое роутер
задаёт через `mmr_lambda`; V2 (complex впереди якорей) и V3 (чередование) — снимают защиту
«прямую норму simple не вытеснить».

Сжатые оценки реранкера (G001: 0.9995…0.9965) не ломают отбор: штраф за повтор почти одинаков
для чанков одного документа, поэтому порядок внутри документа остаётся реранкерским, а штраф
поднимает 1–2 чанка другого документа.

Входы LangSmith: G001 `01a11fd8-c772-7232-a031-52437c041a6d`, G020
`01a11fe5-4faf-7932-9909-c48ee34d0ed5` (project `04aba4b6-a9cc-4fb3-ae7c-f5f95ad2fc70`).

## Приёмка (вариант «а», решение Петра 12.10)

1. Regression-тест на записанных входах G001/G020 (фикстуры — урезанный `inputs` из трейсов,
   без внутренних текстов сверх нужного): цели в `_candidates(...)[0]["passages"]`. Падает на
   текущем коде, зелёный после правки.
2. Юнит-тесты правила: якоря впереди и в исходном порядке; лимит 24; без дублей с якорями;
   пустой snapshot; пустая complex-попытка; кандидат с высоким `rerank_score` и низким
   `vector_score` выбирается раньше обратного.
3. Тест `TestPhase1MMRPrefersVectorScore` переписывается: он закреплял баг. Новое ожидание —
   `rerank_score` раньше `vector_score`; кандидат только с BM25-оценкой по-прежнему проигрывает
   векторному при отсутствии `rerank_score`.
4. CI-гейт `pytest -m "not integration and not slow"` — сверка с базой предсуществующих красных
   тестов (`CLAUDE.md` проекта).

Платных вызовов нет. Замер на 133 вопросах — отдельным шагом после переиндексации (порядок
Петра 12.10: склейка → переиндексация → замер 133 и подбор `FINAL_MERGE_TOP_K` 24/16/12).

## Риски

- Два примера — не доказательство: влияние на остальные complex-вопросы не измерено до
  замера 133.
- Меняется состав `merged` для всех complex-запросов → возможен сдвиг доли `merged` /
  `last_attempt` / `fallback_snapshot` в телеметрии.
