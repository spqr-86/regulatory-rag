Модуль 05 — онлайн-мониторинг для regulatory-rag

Спек · 05.09.2026 · LLM Zoomcamp, модуль 05 · проект ~/projects/ai/regulatory-rag

Задача

Пайплайн v7 отвечает на вопросы по НПА, и с шага 4a умеет считать, во что обошёлся каждый запрос: src/v7/usage.py собирает токены по вызовам, граф копит их в состоянии под ключом llm_usage, eval/pricing.py переводит в деньги. Но живёт это ровно до конца процесса: eval-прогон печатает сводку в файл, а запрос живого человека из Streamlit не оставляет следа вообще. Ни истории, ни динамики, ни ответа на вопрос «стало лучше или хуже, чем месяц назад».

Модуль 05 закрывает именно это: каждый запрос — строка в базе, поверх базы — дашборд, рядом с ответом — кнопки 👍/👎, чтобы у качества появился источник, не зависящий от синтетического эталона. Аудит покрытия 01.09.2026: из модуля 05 не сделано ничего, это самый большой незакрытый пробел под вывеску «Production RAG».

Что уже решено (интервью 05.09)

АудиторияПортфолио и курс — главное; собственный рабочий инструмент — вторым. Значит стек должен читаться на собесе, а не только работать.
Хранилище и дашбордPostgreSQL + Grafana в docker-compose. Ни Postgres, ни ORM в зависимостях сейчас нет — слой заводится с нуля. Compose всё равно нужен под AI Dev Tools, модуль 3.
Точка врезкиВнутри пайплайна v7, с полем source (ui / api / eval / mcp). Причина: app.py вызывает граф напрямую, минуя api.py — middleware на FastAPI не увидел бы собственный Streamlit.
Граница «готово»Телеметрия + 👍/👎 и панель по фидбеку. LLM-судья на живом трафике — вне объёма, отдельным issue: он удваивает цену запроса и сам ещё не валидирован (issue #8).
РазвёртываниеЛокально, docker-compose. Деплой на netcup — отдельным issue: машина боевая с 01.09, но на 2 CPU / 3.8 ГБ RAM там уже живут assistant-web, туннели и xray, и стек Postgres + Grafana + Streamlit + индекс Chroma туда влезает тяжело. Это вопрос ресурсов, а не готовности сервера.

Что пишем на каждый запрос

Единая строка события — общая для всех вариантов ниже; отличаются они только тем, как она доезжает до базы.

query_id        uuid        сквозной id запроса
ts              timestamptz время начала
source          text        ui | api | eval | mcp
question        text        текст вопроса
path            text        simple | complex | clarify | abstain  (маршрут графа)
answer_len      int
n_passages      int         сколько пассажей ушло в LLM
latency_ms      int         полное время ответа
prompt_tokens   int         сумма по вызовам
completion_tokens int
cost_usd        numeric     посчитан по eval/pricing.py
models          jsonb       разбивка по вызовам: модель, узел, токены (llm_usage как есть)
unpriced_models text[]      модели без прайса — чтобы дешёвый отчёт не соврал
error           text        null, если всё прошло

feedback:  query_id (FK), ts, verdict (+1 / -1), comment text null

Варианты реализации

A. Синхронная запись из графарекомендуется

Отдельный модуль src/v7/telemetry.py: после терминального узла графа собирает событие из состояния и пишет строку в Postgres через psycopg (пул на приложение). Запись обёрнута так, что любое исключение БД логируется и глотается — мониторинг не имеет права уронить ответ пользователю.

    Плюсы
  • Один шов, ровно там, где уже собирается llm_usage. Цена считается один раз.
  • Ловит все входы разом — Streamlit, FastAPI, MCP, eval-прогоны, — потому что все они идут через граф.
  • Нет ни очередей, ни воркеров, ни отдельного процесса: меньше всего того, что может молча сломаться.
    Минусы
  • +10–30 мс к каждому запросу (на фоне 5–14 секунд ответа — шум).
  • Пайплайн получает знание о базе; ослабляется тем, что писатель инжектится, а в тестах подменяется на фейк.
  • Пока БД лежит, события теряются безвозвратно.

B. JSONL-журнал + ingest в Postgres

Граф пишет событие строкой в logs/events.jsonl (append-only, без сети). Отдельный скрипт scripts/ingest_events.py заливает журнал в Postgres — по крону или руками перед просмотром дашборда.

    Плюсы
  • Запись не может упасть и ничего не ждёт: файл всегда доступен.
  • История переигрывается с нуля — схему БД можно поменять и залить журнал заново.
  • Работает и без поднятого compose: писать можно всегда, смотреть — когда захотел.
    Минусы
  • Дашборд не живой: между запросом и графиком стоит ingest, который надо не забыть запустить.
  • Второй движущийся кусок (крон/скрипт), молча отваливающийся ровно так, как описано в core.md.
  • На собесе «пишем в файл, потом импортируем» звучит слабее, чем «пишем в Postgres».

C. Callback-слой поверх графа

Пайплайн ничего не знает о телеметрии: он эмитит событие в шину подписчиков (on_query_finished), а подписчиков регистрирует приложение — один пишет в Postgres, другой в лог, третий в тестах копит в списке. Инверсия зависимости в чистом виде.

    Плюсы
  • Граф не зависит от БД совсем; тестируется без единого мока Postgres.
  • Новый потребитель (метрики Prometheus, вебхук) добавляется, не трогая пайплайн.
  • Красиво читается в коде и на ревью.
    Минусы
  • Абстракция ради одного подписчика: у нас он ровно один и второго не планируется.
  • Регистрация подписчиков — новый источник ошибок «а почему ничего не пишется» (в Streamlit с его перезапусками скрипта особенно).
  • Больше кода на тот же результат — против принципа «правлю только затронутое».

D. Сначала прод-трафик, eval потом

Не архитектура записи, а урезание объёма: пишем только запросы живого человека из Streamlit (source = ui), eval-прогоны остаются в файлах, как сейчас. Дашборд показывает реальное использование, история экспериментов не смешивается с историей продукта.

    Плюсы
  • Самый быстрый путь к первому графику.
  • Дашборд не искажён: 56 вопросов eval-прогона не выглядят как всплеск использования.
    Минусы
  • Живого трафика почти нет — дашборд будет пустым, а на скриншоте для портфолио пусто выглядит плохо.
  • Теряется главное: сравнение «до / после» по цене и качеству берётся именно из eval-прогонов.
  • Поле source решает ту же задачу разделения одним WHERE.

Решение

Принято 05.09.2026 (Пётр): вариант A с файловым фолбэком из B. Пишем событие сразу в Postgres изнутри пайплайна; если база не поднята — в файловый журнал, чтобы не терять. Eval-прогоны пишутся тоже, отделяются полем source.

Почему именно он

Вариант A, с одной оговоркой из B: писатель инжектится в граф, а не импортируется им, и рядом с Postgres-писателем живёт файловый — на случай, когда compose не поднят. Так пайплайн остаётся тестируемым (фейковый писатель в тестах), дашборд остаётся живым, и ни одного крона в схеме.

Вариант C стоит взять, только если появится второй потребитель событий; вариант D отвергнут потому, что пустой дашборд бьёт ровно по главной цели — портфолио.

Критерии приёмки

  • docker compose up поднимает Postgres и Grafana; схема применяется миграцией, а не руками в psql.
  • Вопрос, заданный в Streamlit, за секунды появляется строкой в таблице queries — с ценой, латентностью, маршрутом и source = ui.
  • eval/run_v7_eval.py пишет свои запросы в ту же таблицу с source = eval; сводка прогона в файле не изменилась ни на цент (та же арифметика, что и до модуля 05).
  • Остановленный Postgres не ломает ответ: пользователь получает ответ, в логе — предупреждение, событие уходит в файловый журнал.
  • В Grafana есть дашборд: запросы по дням, цена за запрос p50/p95, латентность p50/p95, разбивка simple/complex, доля 👎.
  • Под ответом в Streamlit — 👍/👎; нажатие пишет строку в feedback со ссылкой на query_id и не перезагружает ответ.
  • Панель по фидбеку показывает последние 👎 вместе с вопросом и маршрутом — чтобы промах можно было сразу разобрать.
  • Секреты БД — только из .env; в compose-файле и в репозитории паролей нет.
  • Тесты: событие собирается из состояния графа верно (включая unpriced_models), падение писателя не роняет запрос, фидбек привязывается к существующему query_id. Полный прогон — не хуже нынешних 733 passed / 5 failed.
  • README: как поднять стек, где смотреть дашборд, куда нажимать 👍/👎.
  • Вне объёма: LLM-судья на живом трафике (отдельный issue, после валидации судьи — issue #8).
  • Вне объёма: деплой на netcup и публичный URL (отдельный issue — упирается в память машины, не в переезд).
  • Вне объёма: OpenTelemetry и алертинг — это AI Dev Tools, модуль 4; не дублируем.
