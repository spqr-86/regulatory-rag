Общий поиск для Generic RAG и Department Q&A

Редакция 4 · 19.09.2026 · общий поиск с ограниченной параллельностью · сверено с кодом e9f5cb4. Заменяет редакцию 3. Реализация ещё не выполнена.

Сделать существующий поиск simple → complex доступным обоим сценариям. Department задаёт корпуса и подразделение, получает проверенные нормативные фрагменты, отдельно добавляет профиль объекта и формирует один ответ. Generic сохраняет свой действующий маршрут и формат ответа.

Это ограниченный рефактор с одной новой возможностью: Department получает существующий углублённый поиск. Одного извлечения vector + BM25 в общую функцию недостаточно. Нужно переиспользовать также проверки достаточности, переход в complex и упаковку контекста. Новая универсальная retrieval-платформа для этого не требуется.

1. Анализ подхода

В Department wiring есть отдельный hybrid search, а Generic-граф уже содержит simple, triage, complex и проверку final_context. Польза объединения — доступ Department к этим возможностям и одно место для исправлений retrieval. Улучшение качества и ускорение пока не доказаны.

ПодходОценка
Объединить только hybrid-функциюСамая маленькая правка, но Department остаётся без автоматического complex. Не выполняет обсуждённый сценарий.
Переиспользовать retrieval-часть существующего графаВыбран для этой редакции. Те же узлы и переходы, но возможность остановиться до генерации. Корпуса обрабатываются отдельно и параллельно, с ограниченным доступом к общей модели reranker.
Новый coordinator, объединённый rerank и новый planБольшая миграция ради пока не измеренного выигрыша. Перенесено в «потом».

Упрощение имеет цену: обе ветви могут выполнить complex и вызвать reranker дважды. Раздельные проверки также могут оказаться слишком строгими для короткого ЛНА. Эти риски проверяются небольшим scoped-набором до переключения UI. Обещания «небольшая правка только одной функции» и «точно станет быстрее» исключены.

2. Как идёт запрос

Вопрос + corpora + unit_id + include_object_profile
  ↓
Проверка параметров и профиля
  ↓
Для выбранных корпусов ПАРАЛЛЕЛЬНО (максимум две ветви):
  scoped simple
    → pack → проверка достаточности
      → достаточно: сохранить final_context
      → нужно продолжить: scoped complex → pack → проверка
      → отказ/ошибка: сохранить причину
  ↓
Готовый блок закона + готовый блок ЛНА
  + профиль объекта, если включён
  ↓
Один structured generation call
  ↓
Проверка цитат и статуса ответа

Глубина определяется отдельно для каждого корпуса: например, закон — simple, ЛНА — complex. Повторный complex для того же корпуса не запускается. Обычный Generic проходит тот же retrieval-сегмент один раз на своём настроенном корпусе, затем вызывает свой generator.

Результаты двух корпусов не соревнуются в global top-K. Они сохраняются отдельными блоками до prompt. Незапрошенная ветвь не выполняется. Если общего пригодного нормативного контекста нет, generation не вызывается.

3. Минимальные контракты

RequestContext(
    corpora=("external", "internal"),
    unit_id="unit_moscow",
    include_object_profile=True,
)

retrieve_context(
    question=question,
    filters=compiled_scope,
    runtime=bound_runtime,
    pack_limits=limits,
) -> ScopedRetrievalResult

retrieve_context — тонкий вход в retrieval-часть существующего графа; не новая реализация алгоритма. Его результат: final_context, outcome (ready / empty / insufficient / clarification / failed), route/reason, attempts и elapsed_ms. Для деградации сохраняется technical_failure. При неготовом контексте наружу не выдаётся сырой pool под видом final_context.

Существующий src.v7.state_types.RetrievalPlan сохраняется: top-K, thresholds, MMR и прочие настройки работают как сейчас. RequestContext добавляется отдельно, переименования plan, RetrievalTuning и миграции старых eval-форматов нет. Параметры budget и corpus-local оценки передаются явно; корпуса не выбирает LLM.

RequestContext проверяется на границе Department: corpora непустой и содержит только поддерживаемые значения; unit либо None, либо известный ID. Порядок результатов фиксирован: external, затем internal, независимо от порядка завершения ветвей. Include-profile требует соответствующий unit и доступный профиль. Ошибки ловятся до поиска. При false профиль исключён из prompt, evidence и метаданных ответа.

4. Scope и происхождение фрагментов

ВыборРазрешённый поиск
external; любой unitТолько external документы; подразделение не добавляет ЛНА
internal; unit=NoneТолько общекорпоративные ЛНА
internal; unit=AОбщекорпоративные ЛНА + ЛНА подразделения A
external + internalДве параллельные ветви с этими же правилами

Используются существующие source_type и audience из scope_filter.py. Фильтрация действует до top-K в vector и BM25, затем при section/source fetch, cross-reference, bbox-доборе, pack и fallback. Один и тот же scope передаётся явно; whitelist не может молча выбросить его обязательные поля. Дополнительные Generic filters только сужают выборку.

Внутри одной ветви раскрытие ссылок остаётся в её корпусе и разрешённых документах. Новый межкорпусный resolver не добавляется. Неразрешённая ссылка остаётся в диагностике; она не даёт права ослабить фильтры.

Department работает с V2-корпусом, где ObjectProfile исключён из индекса. Состав проверяется по manifest; старый V1-корпус с листами объектов не включается в новый production-путь. Исторические V1-артефакты сохраняются, сравнения выполняются старой версией кода.

Generic продолжает работать с явно настроенной коллекцией и существующими фильтрами. Рефактор не навешивает новые metadata-фильтры на старый индекс и не объявляет неразмеченные документы external. Новый переключатель корпусов добавляется только в Department. Слияние индексов и миграция Generic metadata отложены.

Сохраняются source, document_id, chunk_id, source_type и применимые unit/snapshot metadata. В Department merge/dedup/fetch опираются на документ, а не только текст или basename. Одинаковые номера чанков разных документов и одинаковый текст не склеиваются. Публичные MCP IDs не меняются. Legacy identity Generic остаётся совместимой; новый ключ применяется там, где есть полная metadata.

5. Переиспользование графа и изоляция ресурсов

У build_graph появляется retrieval-only режим с теми же узлами и условными переходами. На маршруте generate он заканчивается до вызова generator; clarification/abstain также возвращают состояние. Не использовать заглушку generator, которая может случайно дойти до LLM. Generic сохраняет полный граф.

Generic сохраняет intent/domain gate, multi-query и свои visual callbacks. Department входит в router, не добавляя себе centroid domain gate; multi-query и visual enrichment в Department выключены, glossary и основные retrieval-операции общие. Это явные настройки bound runtime, не переключение process-global флагов.

Для Department dual-corpus require_multi_doc внутри каждой ветви выключен: сравнение закона с ЛНА не требует двух документов внутри каждого корпуса. Наличие обеих основ проверяется после получения двух блоков. Single-corpus и Generic сохраняют текущую классификацию вопроса. Остальные пороги первоначально прежние; их изменение — отдельное решение по результатам проверки, не способ скрыть провал миграции.

Vector backend, BM25Index, section/cross-ref callbacks и настройки привязаны к экземпляру графа. Department не должен вызывать глобальную переинициализацию Generic-поиска. Это обязательное условие корректности даже без параллельных ветвей: две страницы Streamlit уже могут обслуживать разные запросы. Достаточно простых зависимостей/замыканий; общий session manager и DI framework не нужны. Для переиспользования вектора добавляется небольшой request-local кеш точных query embeddings; фильтры, graph state и результаты всегда раздельные.

Vector/BM25/RRF, section expansion, rerank, MMR, fallback и pack используют существующие реализации. Все scores сохраняют прежний смысл: distance преобразуется в vector similarity один раз, BM25/RRF/rerank не подменяют dense score в gate.

5.1. Параллельность и оптимизации первого этапа

Две ветви запускаются в ограниченном общем executor, одна ветвь не создаёт вложенный пул. У каждого вызова свои state, pack cache и recorder; общие BM25/index snapshot доступны на чтение. Проверка backend на конкурентный доступ входит в integration gate. При необходимости блокируется только небезопасная backend-операция, а не весь поиск.

Executor имеет конечный лимит workers и принятых задач; лимиты задаются конфигурацией. Общий retrieval deadline включает ожидание очереди и reranker. Перед каждой дорогой стадией проверяется оставшееся время. При ошибке одной обязательной ветви отменяются ещё не начавшиеся задачи, уже выполняющиеся проверяют cancellation между стадиями. Поздний результат не попадает в UI или другой запрос. Blocking-вызов нельзя обещать принудительно остановить: его собственный timeout ограничивает занятый worker; возврат ошибки не должен зависеть от ожидания shutdown нового пула.

Начальные значения deadline выбираются по baseline и фиксируются до cutover. Существующие plan.timeout_ms не считать уже действующими end-to-end deadlines. Progress-события из workers передаются через очередь и отображаются только основным UI-потоком; worker не вызывает Streamlit и не дописывает результат в общий mutable список.

Делаем сейчасОснование в коде и ограничение
Параллельные scoped-ветвиExternal и internal независимы. Сетевое ожидание может перекрываться; generation начинается после завершения обеих. В sequential режиме того же кода можно снять контрольный замер.
Один embedding точного текста в Department-запросеText search Chroma каждый раз вызывает embed_query; добавляем адаптер поиска по готовому вектору. Ключ: точный подготовленный текст + embedding model/revision/dimension. Два concurrent запроса одного ключа разделяют одно вычисление; complex использует его повторно. Кеш исчезает после запроса. Ошибка общая для ожидающих; бесконтрольных повторов нет. Transport retry считается отдельно.
Общая модель reranker, загрузка по необходимостиСейчас init_v7_pipeline конструирует модель сразу. В новом runtime один ресурс на model/device/config внутри процесса, с защищённой ленивой инициализацией. Загрузка и predict сериализованы на этом ресурсе, включая запросы Generic. Две complex-ветви могут сделать два predict, но не одновременно на общей модели. Ожидание lock ограничено deadline; lock не охватывает vector/BM25/pack/generation.
Один BM25 index на неизменяемый snapshotДве ветви используют существующий индекс стека, не строят его на каждый запрос или corpus. При изменении snapshot пересобирается ресурс; фильтры и результаты не кешируются глобально.
Ограниченный section fetchСейчас get_by_filter(limit=50) вычитывает все страницы, затем bridge берёт [:50]. Добавляем отдельный bounded fetch для section expansion: читается только тот же префикс в том же порядке. Полное чтение cross-ref/MCP сохраняется; нельзя менять смысл limit у существующего API.

Department без multi-query использует один подготовленный glossary-текст, поэтому обычный dual-corpus запрос требует одно успешное вычисление embedding, даже при переходе в complex. Это не глобальный кеш ответа. Поиск с разными filters/top-K выполняется отдельно. Разные тексты/embedding spaces никогда не разделяют вектор; Generic domain gate и multi-query сохраняют прежнее поведение и не входят в этот invariant.

В установленной Chroma-обёртке есть поиск по вектору; его raw score остаётся distance. Тест должен доказать одинаковые IDs/distances для text/by-vector поиска. Название метода с relevance_scores не является основанием повторно нормализовать score.

Последовательный контроль использует тот же runtime с workers=1, параллельный — две разрешённые ветви. При отсутствии конкуренции время может приблизиться к максимуму длительностей двух ветвей вместо их суммы, но общий reranker и очередь ограничивают этот выигрыш. Поэтому сравниваются отдельно retrieval_ms и полное время ответа, cold/warm model и rerank_wait_ms.

6. Контекст, профиль и один ответ

Для Department остаётся ограничение до 8 нормативных passages на корпус — текущий TOP_K_PER_LEVEL. Ограничение применяется внутри pack до проверки достаточности. Кандидатов для поиска и rerank может быть больше. После ready нельзя обрезать или расширять этот контекст.

Перед поиском рассчитывается доступный бюджет нормативного текста с учётом вопроса, инструкции, structured schema, целого профиля, запаса на ответ и schema retry. Для двух корпусов этот бюджет делится поровну; для одного он доступен целиком. Автоматическое перераспределение и подбор квот не реализуются. Если обязательный prompt не помещается, возвращается ошибка бюджета, без скрытой обрезки полей профиля.

Готовые блоки складываются без общего ranking. Только перед prompt присваиваются ext_/int_ citation IDs; registry содержит именно отправленные фрагменты плюс включённый профиль. Проверка допустимых уровней цитат сохраняется.

Новая версия Department prompt сообщает, какие корпуса запрошены и какие дали пригодный контекст. Валидатор требует основу только для запрошенного корпуса. Без профиля запрещены object_facts и выводы о применимости к конкретному объекту. Сохраняются проверки unknown-полей; они ловят известный класс нарушений, но не гарантируют семантическую правильность каждого вывода.

Один финальный generation stage, существующий один schema retry. Транспортные retries — по существующим настройкам клиента. Экспериментальный verifier не включается в UI; основной сравнительный прогон выполняется без него. Generic prompt/модель и его generation не меняются.

8. UI и минимальные измерения

Department получает выбор «Закон / ЛНА / Закон + ЛНА» и переключатель «Учитывать данные объекта». По умолчанию — оба корпуса, профиль включён при доступном выбранном объекте. Без профиля переключатель недоступен. Смена любого параметра context сбрасывает показ старого ответа. Существующая страница Generic сохраняется.

В существующие логи/eval-записи добавляются requested corpora, unit, profile flag, для каждого корпуса route/reason и число final passages, retrieval_ms, queue_wait_ms, embedding computations/API attempts/cache hits, rerank calls/candidates, rerank_load_ms, rerank_wait_ms, rerank_predict_ms, llm_ms, total_ms. Незапрошенная ветвь помечается not_requested. Новая система telemetry, схема Postgres и Grafana-панели не требуются. Внутренние corpus-вызовы не записываются как отдельные пользовательские запросы Generic. Retrieval total — wall-clock от постановки до готовности/ошибки обеих ветвей, а не сумма их timings.

9. Приёмка

  • ☐ Generic и Department используют одни узлы поиска, pack и policy simple → complex; отдельный Department hybrid path удалён из production.
  • ☐ Generic на фиксированных результатах backend сохраняет route, scores, ordered final_context и fallback; действующие generation/UI/API контракты совместимы.
  • ☐ Department действительно может пройти simple → complex; retrieval-only ни разу не вызывает generator.
  • ☐ Для закона и ЛНА допустимы разные маршруты; их готовые блоки сохраняются отдельно и попадают в один ответ.
  • ☐ Scope соблюдается на vector/BM25/section/cross-ref/pack/fallback, включая совпадающие source/chunk IDs у разных подразделений.
  • ☐ ObjectProfile не ранжируется; false исключает его полностью; mismatch/unavailable проверяются до I/O.
  • ☐ Два графа с разными ресурсами не переключают друг другу store, BM25 или callbacks.
  • ☐ Corpus-specific проверка ответа, обработка отказов и сброс UI-context покрыты тестами.
  • ☐ Prompt содержит ровно проверенные passages; оба блока соблюдают общий бюджет; citation registry не содержит неотправленные candidates.
  • ☐ Scoped cases включают один короткий ЛНА, сравнение «один закон + один ЛНА», пустую ветвь и переход только одной ветви в complex.
  • ☐ Generic regression и Department pair/traps выполнены с зафиксированными baseline/config; новых scope/citation нарушений и запрещённых выводов нет. Изменения полезности ответов разобраны по вопросам.
  • ☐ Barrier-тест подтверждает перекрытие ветвей; один corpus не запускает вторую. Обратный порядок завершения не меняет порядок evidence и citation IDs.
  • ☐ Одна инициализация модели на общий ресурс; максимум один одновременный predict. Simple-путь не загружает reranker. BM25 не пересобирается на запрос.
  • ☐ Exact-text embedding вычисляется один раз на Department-запрос; обе ветви и complex его переиспользуют; разные ключи и запросы изолированы.
  • ☐ Bounded section fetch возвращает тот же префикс; API полного чтения не меняется. Нет лишнего чтения оставшихся страниц.
  • ☐ Deadline/переполнение очереди/ошибка ветви завершают запрос без generation; late results не изменяют UI, число workers/ожидающих задач ограничено.
  • ☐ Сняты три сопоставимых замера: старый pipeline, новый workers=1, новый parallel. Parallel и sequential дают одинаковый retrieval-контекст на fixed fixtures; real latency измерена отдельно от изменения качества Department.

Небольшой scoped-набор проверяется до production cutover. Если общие thresholds систематически отвергают полезный контекст ЛНА, реализация не считается принятой: сначала разобрать причины, затем отдельной правкой согласовать corpus-настройки. Ослабление порогов ради зелёного eval и замена реального результата заглушкой запрещены.

10. Потом — только при подтверждённой необходимости

ОтложеноЧто должно показать необходимость
Кеш embeddings между разными пользовательскими запросами; перенос reuse в GenericRequest-local reuse уже входит в текущую работу. Дальнейшее расширение — только при измеримой доле повторов и явной политике инвалидирования; учитывать domain gate и multi-query
Больше двух ветвей, nested parallelism, одновременные predict или GPUТекущие две ветви с сериализованным reranker не укладываются в измеренный бюджет ожидания; профиль показывает, какая стадия ограничивает результат
Один объединённый CrossEncoderДва rerank-вызова дают измеримый bottleneck; paired eval подтверждает сохранение обеих нормативных основ
Динамические quotas и controlled global mergeФиксированные отдельные блоки теряют важные evidence или расходуют бюджет впустую; есть конкретные размеченные случаи
Новый RetrievalPlan, session cache и универсальный coordinatorПоявились новые реальные сценарии, которые текущий граф и небольшой RequestContext не выражают без дублирования
Объединение индексов, Generic corpus UI, миграция metadataНужен пользовательский сценарий совместного поиска в этих данных; заранее проверены состав коллекций и миграция

Полная stage telemetry, распределённый scheduler и новые dashboardsМинимальных логов и ограниченного executor недостаточно для подтверждённой нагрузки. Базовые deadline/cancellation проверки входят в текущую работу
LLM planner, multi-agent, retrieval microserviceНового подтверждённого требования сейчас нет; не включать по умолчанию даже в следующую итерацию

Не затрагиваются интерактивный «распрос», нормотворческая формализация, исправление chunking и замена моделей/базы. Отложенные пункты не блокируют принятие текущего объёма и не входят автоматически в следующий PR.

План предусматривает четыре последовательных PR с проверяемыми результатами. Этот документ задаёт объём будущей реализации; он не подтверждает уже работающий новый pipeline.
