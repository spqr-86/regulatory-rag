# Regulatory RAG — Final Streamlit Portfolio Demo Spec

## 1. Назначение интерфейса

Streamlit — это публичная portfolio-demo витрина **Regulatory Compliance Assistant для распределённой организации**.

Система отвечает на вопросы подразделений с учётом трёх типов данных:

- внешние нормативные требования;
- локальные акты организации;
- факты конкретного подразделения / объекта.

Главная ценность интерфейса — не сам факт генерации ответа, а демонстрация того, **почему ответу можно доверять**.

---

# 2. Главный UX-принцип

Если элемент не помогает быстро понять, **почему этому ответу можно доверять**, он не должен находиться в основном пользовательском потоке.

Если элемент объясняет техническое устройство системы, но не влияет на решение пользователя, он должен находиться в `Technical details`.

---

# 3. Основной пользовательский путь

Единственный главный flow:

`Подразделение → Вопрос → Evidence status → Ответ → Применение → Основания → Источники`

Не создавать параллельные сценарии и лишние страницы.

---

# 4. Что должен понять hiring manager за 30–60 секунд

После одного запроса должно быть очевидно:

1. Пользователь выбирает конкретное подразделение.
2. Система учитывает его характеристики.
3. Запрос проходит retrieval и evidence check.
4. Система может ответить, запросить уточнение или отказаться.
5. Ответ связан с конкретными нормативными основаниями.
6. Видно, как:
   `факт подразделения → требование → вывод`.
7. Все источники можно раскрыть и проверить.
8. Техническая архитектура доступна, но не мешает UX.

---

# 5. Общая структура интерфейса

Приложение имеет два основных состояния:

## State A — до запроса

Минимальный экран:

- заголовок;
- выбор подразделения;
- краткий профиль объекта;
- 2–3 примера вопросов;
- поле ввода.

## State B — после запроса

Показываются:

- выбранный контекст;
- вопрос;
- evidence status;
- ответ;
- применение нормы;
- основания;
- все источники;
- technical details;
- поле следующего вопроса.

Отдельную страницу результата не использовать.

# 6. Sidebar

Sidebar должен быть минимальным.

## Обязательное

**Regulatory Compliance Assistant**

Навигация:

- Главная
- О системе

## Опционально

- История

Только если история реально реализована.

## Вторичная линия продукта

Generic Regulatory RAG (поиск по ГОСТ/СНиП/СП) **не удаляется**: он остаётся отдельной
вторичной страницей «Общий поиск» вне главного пользовательского потока. Ссылка на неё
допустима в sidebar, но main-flow — только Department Q&A. Причина: README продаёт проект
как две продуктовые линии, и витринный eval 56 goldenset относится именно к generic-линии.

## Не размещать в sidebar

- model provider;
- embedding model;
- DB path;
- collection;
- reindex;
- source count;
- V7/V8;
- prompt version;
- технические настройки.

# 13. Evidence status

Evidence status обязателен для каждого запроса.

Он визуально идёт **до ответа**.

---

## 13.1 Sufficient evidence

Зелёный status block:

**✓ Доказательств достаточно**

Подпись:

> Ответ основан на нормативных источниках, локальных актах и данных подразделения.

---

## 13.2 Clarification required

Amber block:

**Нужно уточнение**

Подпись:

> Для проверки применимости требования не хватает данных об объекте.

Ниже конкретный вопрос:

> Есть ли на объекте круглосуточное пребывание людей?

Ответы:

`Да` `Нет` `Не знаю`

После уточнения запрос продолжается.

**Границы P0:** на витрине показывается только корректное отображение вопроса (P0a).
Полноценный continuation (ответ → правка typed field → повторный запрос) — **вне P0** и
**не должен мутировать снапшот объекта**: `ObjectProfile` неизменяем, его `content_sha256`
и `as_of_date` держат воспроизводимость eval. Когда continuation будет делаться, ответы
пользователя передаются как отдельный эфемерный `overrides` в `answer_question`, а лист
объекта не перезаписывается.

---

## 13.3 Insufficient evidence

Amber / neutral warning:

**Недостаточно оснований для надёжного ответа**

Подпись:

> Система не нашла достаточно подтверждений и не стала формировать уверенный вывод.

Дополнительно показать причину.

Например:

> Не найден локальный акт, регулирующий этот вопрос.

---

## 13.4 Out of scope

**Запрос вне области базы знаний**

Подпись:

> Доступные источники не покрывают этот вопрос.

Общая LLM не должна пытаться отвечать вне корпуса.

---

# 14. Ответ

После successful evidence status:

## Ответ

Это главный текстовый блок.

Требования:

- 1–3 коротких абзаца;
- прямой вывод;
- без длинной юридической простыни;
- без повторения retrieved chunks.

Пример:

> Для Московского филиала плановая проверка проводится не реже одного раза в год.

> После технического обслуживания систем противопожарной защиты проводится дополнительная внеплановая проверка.

---

# 15. Почему такой вывод

Следующий блок должен быть центральным демонстрационным элементом.

## Почему такой вывод

Показывается цепочка:

`Факт → Требование → Вывод`

Пример:

### Факт

`24 сотрудника · круглосуточного пребывания нет`

↓

### Требование

`Плановая проверка проводится не реже одного раза в год`

↓

### Вывод

`Для данного подразделения требуется ежегодная проверка`

Этот блок должен быть визуально заметнее карточек источников.

---

# 16. Основания ответа

Под цепочкой:

## На чём основан ответ

Три компактные категории.

### Внешнее требование

**Правила противопожарного режима**

`п. 4.2.3`

При необходимости — короткий excerpt.

---

### Локальный акт

**Положение о пожарной безопасности**

`п. 3.1.1`

При необходимости — короткий excerpt.

---

### Факт подразделения

- 24 сотрудника
- круглосуточного пребывания нет

Не показывать большие raw chunks.

---

# 17. Конфликт источников

Показывать только если реально найдено расхождение.

## Обнаружено расхождение

### Внешнее требование

...

### Локальный акт

...

### Как обработано

Например:

> Локальный акт устанавливает более строгое требование.

или:

> Требуется проверка специалистом.

Этот блок не должен присутствовать постоянно.

---

# 18. Источники, на которые опирается ответ

После основных выводов:

`Источники, на которые опирается ответ (7) ▾`

По умолчанию collapsed.

Название сознательно не «Все источники»: `DepartmentResponse.evidence` содержит **только
процитированные** фрагменты (`service.py`), а не всю выдачу retrieval. Показывать под
заголовком «все» — вводить в заблуждение. Выдача retrieval целиком в контракт не
добавляется; это возможно позже, отдельным решением.

Внутри:

- название документа;
- тип источника;
- locator;
- relevant excerpt;
- retrieval score (для object-профиля — `None`: это не retrieval-хит);
- metadata при необходимости.

Raw chunks допускаются только здесь.

# 25. Visual guidelines

Интерфейс должен быть:

- светлым;
- спокойным;
- с большим количеством whitespace;
- без декоративной перегрузки;
- с минимальным количеством borders;
- с одним основным accent color;
- зелёный — только success;
- amber — clarification / insufficient;
- neutral/red — out of scope или критическое расхождение;
- одинаковые radius и spacing;
- без попытки выглядеть как полноценный enterprise SaaS.

Цель — инженерный продукт, а не маркетинговый dashboard.

# 30. Критерий готовности

Streamlit считается готовым к portfolio demo, если человек без чтения README после одного запроса может ответить на следующие вопросы:

- Какое подразделение выбрано?
- Какие факты о нём учитывались?
- Хватило ли системе evidence?
- Какой ответ получен?
- Почему система пришла к этому выводу?
- Какие внешние документы использованы?
- Какие ЛНА использованы?
- Какие факты объекта повлияли на решение?
- Может ли система отказаться отвечать?
- Можно ли проверить найденные источники?
- Можно ли раскрыть техническую реализацию?

Если ответы очевидны из интерфейса — UX выполняет задачу.

# 32. Принятые решения по реализации (18.09)

1. **Generic RAG сохраняется** как вторичная страница «Общий поиск», вне main-flow (см. §6).
2. **«Все источники» → «Источники, на которые опирается ответ»**; используется только
   `DepartmentResponse.evidence` (cited), retrieval score — только для retrieval-хитов (см. §18).
3. **Clarification continuation — вне P0.** Снапшот объекта неизменяем; будущий continuation
   идёт через эфемерный `overrides`, не через правку листа (см. §13.2).
4. **Verifier в UI не включается.** По прогону 17.09 он давал ложные `verification_*` на
   верных ответах. Статусы `insufficient_evidence` и `conflict` строятся из reason_codes
   `decide()` и без него.
5. **Приоритет маппинга статусов фиксируется таблицей** в presentation-слое и покрывается
   regression-тестом: insufficient/OOS никогда не показывают уверенный ответ.
