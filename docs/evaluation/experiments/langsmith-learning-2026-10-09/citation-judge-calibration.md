# Первые проверки судьи нормативных ссылок

09.10.2026. Учебные примеры, не правовая верификация и не оценка реальных ответов RAG. Запуск на сервере через OpenRouter, модель openai/gpt-4o, temperature=0.0, JSON mode, max_retries=0. Каждый вызов отдельно согласован.

| Пример | Ручная оценка | Ответ судьи | Совпадение |
|---|---|---|---|
| Ответ ссылается на п. 30; контекст указывает п. 31 | fail | fail | Да |
| Ответ и контекст указывают п. 31 | pass | pass | Да |
| Ответ указывает п. 31; в контексте указаны только документ, раздел и текст требования | needs_review | pass | Нет |

Последний ответ судьи:

> Ссылка на пункт 31 раздела III Правил №2464 подтверждена фрагментом 1, где указано, что продолжительность стажировки должна составлять не менее двух смен.

В последнем контексте номер пункта отсутствует: «Раздел III: продолжительность стажировки на рабочем месте должна составлять не менее двух смен». Перед вызовом отдельно проверено отсутствие числа 31 в context. Номер 31 присутствует только в проверяемом ответе.

Установленная ошибка: судья заявил подтверждение реквизита, которого нет в предоставленной опоре. Нельзя установить по этому ответу, взял ли он номер из памяти или перенёс из проверяемого ответа. JSON и parse_verdict при этом работают правильно.

Следующий шаг: уточнить промпт — для каждого подтверждаемого реквизита требовать его наличия в тексте/заголовке/метаданных контекста; явно запретить использовать ответ системы как доказательство самого себя. Если номер есть только в ответе, без подтверждения или опровержения в контексте, ожидать needs_review. После изменения повторить отрицательные и положительные контрольные примеры только по согласию Петра.

Три примера — начальная диагностическая проверка, а не достаточная выборка для вывода о надёжности судьи. Ранее ответ в Markdown вызвал JSONDecodeError; после включения JSON mode формат разобран успешно.

## Повтор после уточнения промпта

Пётр добавил: «Ответ системы не является доказательством своей ссылки. Если номер пункта указан только в ответе, а фрагменты не позволяют подтвердить или опровергнуть его, ставь needs_review». Правка перенесена на сервер, наличие её в отрендеренном промпте проверено. Данные примера без номера пункта не изменялись.

Один согласованный вызов вернул fail вместо ожидаемого needs_review:

> Ссылка в ответе на пункт 31 раздела III Правил №2464 не подтверждена фрагментом. Фрагмент 1 содержит информацию о документе и разделе, но не указывает на пункт 31. Доступные реквизиты во фрагменте не совпадают с указанными в ответе.

Судья теперь заметил отсутствие номера, но спутал отсутствие подтверждения с противоречием. В контексте нет другого номера, который опровергал бы 31. Поэтому fail не подтверждён входными данными. Код и разбор JSON завершились успешно; критерий неопределённости всё ещё не проходит.

Следующий шаг: сделать различие в определениях оценок явным — неверность требует противоречащего реквизита, отсутствие номера в опоре означает неопределённость; доступный реквизит, пропущенный в ответе, остаётся нарушением. Повторить проверку после согласованной правки, затем проверить остальные контрольные случаи и новые аналогичные примеры. Один удачный повтор не докажет устойчивость.

## Полная переработка промпта и три вызова

По поручению Петра весь промпт прочитан и переписан. Для каждого реквизита отдельно определены совпадение, доступный реквизит, пропущенный в ответе, противоречие и недостаток доказательств. Отсутствие номера в обрезанном фрагменте не считается ни противоречием, ни доказательством неприменимости пункта. В примерах самого промпта использованы номера 71/72, а не номера контрольного примера 30/31.

run_citation_example.py теперь последовательно запускает три случая и печатает ожидаемую оценку, фактический вердикт и совпадение. До API-вызовов с подставной моделью проверены все входы, подстановка промпта, JSON mode и отсутствие повторов. Правки перенесены на сервер. Выполнены ровно три согласованных вызова, по одному на случай.

| Случай | Ожидание | Получено |
|---|---|---|
| В ответе п. 30, в контексте п. 31 | fail | fail |
| В ответе и контексте п. 31 | pass | pass |
| В ответе п. 31, в контексте номера нет | needs_review | needs_review |

Объяснение третьей оценки: «Фрагмент 1 подтверждает документ и раздел, но не содержит номера пункта. Номер пункта 31 нельзя ни подтвердить, ни опровергнуть».

Все три ответа были корректным JSON и успешно прошли parse_verdict. Наблюдаемый итог — 3/3 совпадений с ручными ожиданиями на этих контрольных случаях. Это подтверждает исправление поведения в данном прогоне, но не устойчивость на других примерах или повторах.

Машиночитаемые результаты и SHA-256 файла с промптом: citation-judge-three-cases-results.json. Фабрика модели, граф RAG, индекс и датасет не изменялись. Push в GitHub не выполнялся; файлы перенесены на сервер через SCP.

## Перенос на реальный ответ G019

Из сохранённого трейса G019 получен фактический Input генератора. Выделен точный блок фрагментов, без инструкций исходного генератора. Вопрос и ответ взяты из сохранённого состояния того же прогона. Входы и ручное ожидание сохранены в citation-judge-g019-real-case.json.

Фрагмент 3 содержит источник 1479 ппр, раздел I «Общие положения» и пункт 9. Ответ называет источник и п. 9, но не указывает раздел. По согласованной рубрике ожидается fail за пропуск доступного реквизита.

Один отдельно согласованный вызов того же судьи вернул pass:

> Документ '1479 ппр', раздел 'I. Общие положения', пункт 9 подтвержден фрагментом 3, где указано, что тренировки по эвакуации должны проводиться 'не реже 1 раза в полугодие'. Все применимые реквизиты совпадают.

Ожидание не совпало с оценкой. Раздел найден в контексте, но не указан в ответе: судья не применил правило о пропуске реквизита. Точную внутреннюю причину решения установить нельзя. API и JSON-разбор завершились успешно; повторных вызовов не было, RAG не запускался.

Результат: citation-judge-g019-real-result.json. Следующая возможная правка: требовать раздельно выписать фактическую ссылку из ответа и реквизиты из фрагмента; отсутствие раздела в первой записи проверять как пропуск, а не заменять реквизитом из второй. Три успешных учебных случая не подтвердили переносимость на реальный ответ.

DeepSeek на G019 заявил: «Документ, раздел и номер пункта совпадают с указанными в ответе», хотя раздел I в ответе не указан. Это тот же наблюдаемый сбой сравнения наличия реквизита в ответе.
