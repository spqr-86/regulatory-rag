# Эксперимент: нарезка законов и правил на чанки (A/B, 17.10.2026)

Статус: прогон выполнен 17.10.2026; протокол был зафиксирован до замера, результаты — в разделе
«Результаты» ниже. Дизайн нарезки —
[design/2026-10-17-law-chunking-design.md](../../design/2026-10-17-law-chunking-design.md).

## Вопрос

Находит ли поиск нужную норму лучше, если резать текст законов по структуре (статья →
часть → пункт → подпункт, вводная перечня не отрывается), а не по токенам HybridChunker?
Какой лимит чанка (900 / 1800 / 3000 знаков) лучше, и даёт ли что-то префикс «документ →
глава → статья/пункт»?

Зачем: ресёрч Codex (`knowledge/research/codex/2026-10-17-legal-chunking.md`) показал
противоречие — на BGB структура выигрывает, на актах ЕС проигрывает окну 350 слов. Замеров
на русских НПА нет. Структурную нарезку внедряем только если она выигрывает на нашем
корпусе.

## Что остаётся одинаковым

| Параметр | Значение |
|---|---|
| Корпус | 7 документов: `2464`, `тк рф`, `426-ФЗ`, `О пожарной безопасности`, `1479 ппр`, `782н`, `776н`. Приказы с таблицами (29н, 223н, 817н) и мелкие статьи не входят — таблицы это отдельная линия |
| Текст | один на все варианты: `source_docs/` через `pymupdf` (PDF) и как есть (`2464.md`); вариант C — исключение, см. ниже |
| Эмбеддер | `text-embedding-3-small` через `get_embedding_model()` (OpenRouter), как в проде |
| Вопросы | 133 уникальных вопроса `eval/data/golden_retrieval_labeled.jsonl` (90 практических + 43 синтетических) |
| Поиск | dense (косинус), BM25 (префикс-стеммер 5 знаков), гибрид RRF k=60. Без реранкера и без LLM |

Не меряем: генерацию ответа, реранкер, таблицы, редакции законов.

## Варианты (одна переменная — нарезка)

| ID | Нарезка |
|---|---|
| **C** | Текущая: HybridChunker, снимок `build-8cs1plb3` (прод). Берётся из индекса как есть, текст 2464 — из `2464.md`, остальные — из PDF через Docling |
| **W350** | Окно 350 слов, шаг 300, без структуры и префикса (контроль «глупое окно», выигравшее на актах ЕС) |
| **P** | Абзацная: логический абзац = чанк; абзацы короче 200 знаков склеиваются со следующим; без префикса |
| **S900 / S1800 / S3000** | Структурная: статья/пункт целиком, если влезает; иначе по частям, затем по подпунктам с вводной в каждом чанке, затем по предложениям. Префикс «документ › раздел › статья/пункт» в тексте чанка |
| **S1800-np** | S1800 без префикса (изолирует эффект префикса) |

## Метки и как сравниваем разные нарезки

Метки эталона — id чанков старого индекса (`relevant_chunk_ids`), привязаны к границам
чанков C. Для сравнения разных нарезок метка превращается в **текст-доказательство**: текст
размеченного чанка из индекса `chroma_db` (где эти id существуют, 478/478). Чанк
варианта **покрывает** метку, если содержит ≥60% её слов (≥4 букв) — тот же критерий, что в
`scripts/retrieval_29n_table_context.py`.

Вопрос засчитан, если покрыта хотя бы одна его метка. Контроль: доля меток, которые вообще
покрыты хоть одним чанком варианта («оракул»). Вопросы, у которых нет покрытых меток в
каком-либо варианте, исключаются из сравнения у всех — иначе разница границ текста
(PDF vs Docling) выдавалась бы за качество нарезки.

## Метрики

Главная — **доля вопросов с покрытой нормой при фиксированном бюджете контекста**: берём
чанки по рангу, пока суммарная длина ≤ B знаков (первый чанк берётся всегда). Длинные
чанки не получают преимущества, как при сравнении по top-k.

- Бюджеты B: 4000 / **8000** / 16000 знаков. Заглавный — 8000 (порядок текущего контекста
  генератора, `FINAL_MERGE_TOP_K`=24 при чанках ~400 знаков; точное значение печатает
  отчёт).
- Вторичные: HR@5 и HR@12 по рангу (для сопоставления с прежними таблицами, смещены в пользу
  длинных чанков), средняя доля покрытых меток, число чанков в бюджете.
- Качество нарезки без поиска: число чанков, медиана длины, доля чанков, оборванных посреди
  предложения, доля подпунктов без вводной, покрытие текста (все абзацы исходника лежат в
  каком-либо чанке).
- Разбивка по документам. Доверительный интервал разницы с C — парный бутстреп по
  вопросам (10 000 повторов).

## Правило решения (до замера)

Структурный вариант S* считается лучше C, если при B=8000 на гибридном поиске:

1. прирост доли покрытых вопросов ≥ +3 п.п., и нижняя граница 95% интервала разницы > 0;
2. ни в одном документе с ≥ 15 вопросами просадка не больше 5 п.п.;
3. вариант не хуже W350 (иначе структура не нужна, хватит окна).

Если выигрывает W350 или P — структурный парсер откладывается. Если S* и W350 равны в
пределах интервала — решает простота: окно. Ничья по лимитам — меньший лимит.

## Стоимость и ограничения

Эмбеддинги ≈ 6–7 вариантов × ~1.8 млн знаков корпуса ≈ 3–4 млн токенов ≈ **$0.07–0.1**
(`text-embedding-3-small` $0.02 / 1 млн). Генерации и судьи нет. Скрипт сам печатает оценку
и без флага `--yes` платных вызовов не делает; эмбеддинги кешируются на диск по хэшу текста.

Угрозы валидности:

- Метки пулированы из кандидатов текущей системы — завышают C (и вообще варианты с
  похожими границами). Относительный вывод допустим, абсолютные цифры — нет.
- Текст PDF и Docling различается порядком чтения и шумом колонтитулов; метка по словам
  устойчива, но не идеальна. Контроль — оракул.
- 133 вопроса: разница < ~5 п.п. на всём наборе и < ~10 п.п. по документу — в шуме.
- ТК взят из PDF, не с pravo.gov.ru; редакция не сверена.
- Структурный парсер этого эксперимента — прототип; провал варианта может быть провалом
  парсера, а не идеи. В отчёте это разделяется проверкой качества нарезки.

## Результаты

Полный отчёт — `eval/runs/chunking_ab_2026-10-17/report.md` (+ `results.json`, `run.log`;
кеш эмбеддингов не коммитить). Прогон: 117 вопросов из 118 (один не покрыт в S-вариантах и
исключён у всех), 7 вариантов, эмбеддинги ≈ 5,6 млн токенов ≈ $0.11. Оракул покрытия меток
98–100% у всех вариантов — разница ниже не из-за потери текста.

Доля вопросов, у которых норма попала в контекст (hybrid, бюджет 8000 знаков), разница с C в
п.п. и 95% интервал:

| вариант | доля | разница с C |
|---|---|---|
| C (текущая) | 91.5% | — |
| P (абзацная) | 87.2% | −4.3 [−10.3; +1.7] |
| S1800-np | 84.6% | −6.8 [−13.7; 0.0] |
| S900 | 83.8% | −7.7 [−15.4; −0.9] |
| S1800 | 82.1% | −9.4 [−16.2; −2.6] |
| S3000 | 80.3% | −11.1 [−17.9; −4.3] |
| W350 | 75.2% | −16.2 [−24.8; −7.7] |

**По правилу решения (условие 1 не выполнено ни одним S-вариантом) структурная нарезка не
принимается: на этих вопросах она не лучше текущей, а при равном бюджете хуже на 7–11 п.п.**
Окно W350 хуже всех, то есть «простое окно вместо структуры» тоже не вариант. Префикс не
помог: S1800 без префикса не хуже S1800 (dense 82.1% против 77.8%, разница в шуме).

Качество нарезки (без поиска) структурные варианты улучшают: оборванных посреди предложения
5–8% против 54,5% у C; все абзацы исходника на месте (S1800/S3000), у S900 потеряно 4 абзаца
из ~20 тыс.

Что это значит и что нет:

- Вывод «хуже» ограничен метрикой. Метки эталона — чанки самого C, поэтому C имеет
  встроенное преимущество (пулирование, см. угрозы); это поправка в пользу S, а не против.
- Бюджет в знаках: в 8000 знаков влезает 21 чанк C против 8–9 чанков S. Метрика «хотя бы одна
  метка покрыта» награждает набор из многих мелких кандидатов (разнообразие), а не точность
  каждого. По рангу (top5) S1800 лучше C: 80.3% против 67.5%, top12 равны (88.9% против
  88.0%), но это сравнение смещено в пользу длинных чанков.
- Эксперимент не измеряет то, ради чего затевалась переделка: полноту вводной перечней и
  целую статью в контексте генератора (G005, G047). Метки — «голые» подпункты из старой
  нарезки, их C находит идеально по построению. Качество ответа генератора не мерили.
- По документам: на ТК и 426-ФЗ S заметно хуже C (ТК 59–76% против 88%; 426-ФЗ 59–82%
  против 94%), на 2464 S не хуже (90–94% против 87%). n по документам 2–31, различия до
  ~10 п.п. в шуме.

Решение: **нарезку в проде не менять по итогам этого замера**; `law_chunker.py` в полном
объёме не писать. Для дефектов G005/G047 остаются точечные меры (вводная в чанк подпункта и
склейка частей статьи при выдаче) — их эффект меряется на ответах генератора, а не этим
скриптом. Условие пересмотра: набор вопросов с метками по норме, а не по чанку C, либо
замер ответов генератора на G005/G047-подобных вопросах.
